## 2. 冲突裁决（谁覆盖面广用谁）

### 2.1 `backend/cmd/server/VERSION`
链首 0.0.24 与基线 0.1.178 冲突，取 fork 侧；后续 0.0.25→0.0.29 链自动跟上。

### 2.2 `backend/internal/handler/openai_chat_completions.go`（#10 keepalive 的 handler 半边）
- 上游 #5730（"#5148 对齐"）已收编计费闭包：`submitChatUsage`（闭包内 nil 守卫、错误分支无条件落账）。**取上游**——不设非零 token 门槛覆盖面更广，且 fork 原四字段门槛存在真实漏账面（零 token 但带 `SearchCount`/`WebSearchCalls`/`AudioUsage` 等 mandatory 账单会被丢弃，而 `submitOpenAIUsageRecordTask` 明确把这类账单标记为不许丢）。
- fork 保留另一半（上游没有）：failover 闸门 `openAIForwardMayFailover(...)` + `SafeToFailoverAfterWrite && c.Writer.Written() → streamStarted = true`。该文件相对新基线的剩余差异仅这两处（FORK.md #10 已同步）。
- 复核结论：零 usage 幽灵账单行是上游全系统既有口径（其非 raw 主路径同样超时返回可能全零的 result），如需治理应在 `RecordUsage` 层加统一守卫并提上游，不在调用点设卡。

1. **#10 快照空壳 + verify 空转**（修复 `f241fff40`）：keepalive proposal 触点 bullet 用全角冒号，`fork_overlay.py` 的 `BULLET_RE` 只认半角 → #10 被静默解析为零触点，`cfc5cfa1d` 归档的 manifest 全空、patch.diff 0 字节，verify 对 #10 的 OK 无实义。修复：正则放宽为 `[:：]`、bullet 转半角、陈旧描述同步（闭包半边已收编）、快照重归档（4 补丁文件 + 28.5KB diff）。
2. **passthrough ops 标志误标**（修复 `7d18faa0c`）：上游 v0.1.178 给 `chat_completions`/`responses` 两条 anthropic-native **转换**路径误传 `passthrough=true`（该参语义=「原样直通仅换认证」，全库转换路径惯例传 `false`）；`messages` 为零转换直通，`true` 正确保留。FORK.md ops 行已加守护说明，防下次 rebase 被上游回改。

### 4.2 上游可上报素材（非本 fork 回归，行为与上游逐位一致）
1. **#5730 注释不变量为假 + failover 部分 usage 丢弃**：非 raw 路径 `handleChatStreamingResponse → finalizeStream()` 在「已写真实字节 + 流中途 `response.failed` 判 failover」时返回非 nil result + `*UpstreamFailoverError`，与注释「failover 恒 result=nil」矛盾。不会重复计费（failover 分支全部 return/continue 收束），但该路径已计量的部分 usage 被静默丢弃（`handleFailoverExhausted` 不收 result）——正是 #5148 类漏账；Anthropic 侧 #5154 有显式守卫（errors.As 拦截强制 nil + 零 usage 不返回部分结果），OpenAI 侧移植时两个守卫都没带上，且无测试覆盖。判定依据：该场景 `SafeToFailoverAfterWrite` 恒 false（`newOpenAIStreamFailoverError` 从不置位），fork 闸门与上游旧闸门行为一致，非 fork 放大。
2. **M6 遗留**（上游 #5666 自审明示暂缓）：两个 anthropic-native 转换文件在读到上游首字节前提交 200+SSE 头，空流被合成"成功"且永不 failover。
3. **v0.1.178 tag 自带坏前端测试**：`CreateAccountModal.grok.spec.ts` 在纯上游树上即失败（fork 未触碰该目录；fork CI 关键 spec 清单不含它，不受影响）。
